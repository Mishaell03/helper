# Чёрный фон/след после скрытия и повторного показа

## Подсказка блока: Win32 8 и отменённый показ на Windows 10

Пользователь сообщил об отказе `SetWindowDisplayAffinity` с кодом 8 для отдельной
подсказки. Это не безобидное предупреждение: при отказе Helper намеренно не
показывает окно, иначе текст мог бы попасть в запись. `ERROR_NOT_ENOUGH_MEMORY`
не доказывает нехватку физической памяти — код может относиться к созданию
защищённой поверхности DWM.

В прежнем коде affinity запрашивалась у HWND 0×0 до первого `UpdateLayeredWindow`.
Теперь окно создаётся ненулевого размера, получает начальную поверхность 1×1
с полностью нулевым alpha **без текста и без показа**, затем применяется и
проверяется `WDA_EXCLUDEFROMCAPTURE`. Только после успеха загружается текст;
перед показом affinity проверяется ещё раз. Инициализация больше не зависит от
первого кадра с конфиденциальным текстом. Это исправление порядка создания,
а не подтверждение, что любая Windows 10/драйвер поддержит такую поверхность.

Функция защиты главного окна работает как прежде; в общий helper добавлен только
необязательный выходной параметр для точного кода ошибки. Нет перехода на
`WDA_NONE`/`WDA_MONITOR`, показа без защиты, изменения OBS или внешних процессов.

Проверить новую **полную Windows-сборку** на проблемном ПК (не hot reload).
Если ошибка останется, запустить с `--capture-diagnostics`, переключить несколько
слотов при скрытом Helper и прислать последний `capture-*.log` из
`%LOCALAPPDATA%\Helper\Diagnostics`. В нём появились события
`slot_notification.surface_ready`, `slot_notification.protected`,
`slot_notification.protection_failed` и `slot_notification.show`, HWND, build
Windows, стили и код отказа. Тексты блоков в журнал не записываются. Если после
`surface_ready` снова следует Win32 8, нужен разбор совместимости именно на этом
ПК; подавление предупреждения не обеспечит защиту. Windows GUI/OBS здесь не
проверялись, поэтому подтверждать исправление на Windows 10 пока нельзя.

## Подтверждённое воспроизведение на Windows 10

На Windows 10 Pro 19045, RTX 4060, драйвере `32.0.15.9649` пользовательский
GDI-тест воспроизвёл дефект на `Show cycle 2 (early)`: все 161920 пикселей
захвата 368×440 были чёрными, вместо двухцветного фона. Локально окно было нормальным.
Это не ошибка координат теста и не проблема только одного рекордера. По этим данным
нельзя отделить ошибку DWM, драйвера и взаимодействие с Flutter, но переход
первый показ → скрытие → повторный показ является воспроизводимым триггером.

Предыдущее упрощение рамки/прозрачности **не устранило этот случай**. В новом обходе
на Windows 10 19041–21999 уже показанная панель при скрытии переносится целиком
за пределы виртуального рабочего стола, без `SW_HIDE` и следующего `SW_SHOW`.
Нативная поверхность и `WDA_EXCLUDEFROMCAPTURE` остаются включёнными. При открытии
возвращаются координаты, запрашивается кадр; при скрытии фокус возвращается другому
приложению. При изменении мониторов положение парковки пересчитывается; при потере
прежнего монитора восстановление выполняется на доступном экране.

Это целевой **обход триггера**, не доказанное исправление внутренней ошибки Windows.
Его нужно проверить тем же тестом на проблемном ПК. На Windows 11 остаётся обычное
скрытие. Фоновый старт по-прежнему не показывает окно: парковка применяется только
к уже показанной панели. Если парковка невозможна (например, окно уже минимизировано),
выполняется обычное скрытие; журнал отличает эти случаи. Системный диалог импорта
использует прежний отдельный путь, его исключение по-прежнему не гарантируется.

На Windows 10 `IsWindowVisible` у припаркованного HWND остаётся true по замыслу.
Поэтому сценарии проверяют реальную видимость **на мониторах**, а не только этот
флаг; сравнение захваченных пикселей сохраняется и не ослаблено.

### Подробные логи Release-версии — без Flutter

После установки новой сборки полностью завершить предыдущий Helper и выполнить:

```powershell
& "$env:LOCALAPPDATA\Programs\Helper\helper.exe" --capture-diagnostics
```

Несколько раз скрыть/показать панель и выйти. Открыть папку:

```powershell
explorer.exe "$env:LOCALAPPDATA\Helper\Diagnostics"
```

Прислать последний `capture-*.log`. Он содержит версию сборки, build Windows,
`stable_surface`, события показа/скрытия/изменения позиции, HWND, координаты,
стили, affinity, cloak и состояние фокуса. Файл заполняется даже без ошибок API.
В версии с watchdog заголовок начинается с `Helper capture diagnostics v3` (раньше `v2`), на Windows 10
ожидаются `stable_surface=1` и `hide.parked`. Если заголовка нет, проверить, что
запускается именно новая сборка и что предыдущий процесс был завершён.
Тексты блоков, нажатия клавиш и скриншоты в этот журнал не записываются.
Без флага подробный журнал создаётся только при аварийном срабатывании watchdog.
Тест захвата автоматически включает флаг.
Зависания просмотра, аварийное скрытие и стадии открытия описаны в [responsiveness.md](responsiveness.md).

### Обзор задач Win+Tab

Снимки рабочего стола в обзоре задач Windows не обязательно используют тот же
путь захвата, что рекордер. Поэтому Helper дополнительно скрывается до передачи
Win+Tab оболочке. Сочетание не резервируется через `RegisterHotKey` и не отключается:
его наблюдает отдельный нативный hook. После выхода из обзора панель остаётся
скрытой до обычного хоткея показа. Если шёл ввод/отсчёт, он ставится на паузу.
В диагностике этот переход отмечен `task_view.hide`. Открытие обзора задач кнопкой
панели Windows или жестом тачпада этот обработчик не отслеживает.

## Что было исправлено ранее

### Стандартная рамка при изменении размера

Пользовательское фото подтвердило, что предыдущее исправление watchdog/ghosting
не устранило рамку. Это не следует считать исправленным только по Dart-тестам.
Обнаруженный путь: `WS_OVERLAPPEDWINDOW` оставлял `WS_CAPTION`, а `setAsFrameless()`
в window_manager менял внутренний флаг, не удаляя стиль. Отключение DWM non-client
rendering не запрещает классическую отрисовку рамки через `DefWindowProc`.

Теперь runner создаёт окно без `WS_CAPTION`, сохраняет `WS_THICKFRAME` для resize,
не позволяет вернуть заголовок через `WM_STYLECHANGING` и обрабатывает обе формы
`WM_NCCALCSIZE` и `WM_NCPAINT` до Flutter/plugin delegates. При максимизации
клиентская область ограничивается рабочей областью монитора. Прозрачность,
display affinity и парковка не переключаются во время resize.

`test/native/frameless_window_test.cpp` проверяет реальное тестовое HWND при
многократном изменении размера/стиля; Windows background test проверяет геометрию
у собранного Helper. Эти Windows-проверки и визуальное воспроизведение нужно
выполнить на Windows: в macOS они не запускались.

В старом пути показа сочетались несколько независимых владельцев композиции:

1. `window_manager` задавал прозрачный фон через недокументированный Accent API.
2. `flutter_acrylic` повторно выключал и включал Accent для того же HWND.
3. Каждый показ снова устанавливал стили и `SWP_FRAMECHANGED`, даже если они
   не менялись. Это принудительно пересчитывало нативную рамку.
4. `SetWindowPlacement` восстанавливал сохранённый `showCmd` и мог показать/активировать
   окно до следующего явного `ShowWindow`. Путь отсчёта использовал другую последовательность.
5. Affinity повторно устанавливалась даже при уже действующем `0x11`.

Это подтверждённые по коду лишние переходы DWM, а не доказательство конкретного
дефекта драйвера на каждом ПК. На проблемном оборудовании необходима повторная
запись. По одному описанию нельзя исключить несовместимый метод захвата или Windows.

Теперь прозрачностью управляет только Windows runner: документированная DWM
alpha-композиция с пустой blur-областью, без Accent/Acrylic/Mica backdrop.
Нативная рамка и анимации отключены, полупрозрачную панель рисует Flutter.
Неизменённые стили и уже установленное исключение не перезаписываются на каждом
показе. В обычном пути (Windows 11) позиция после `SW_HIDE` сохраняется самим Windows — восстановления
`SetWindowPlacement` больше нет. Обычный показ и отсчёт используют общий путь,
при этом отсчёт не перехватывает фокус.

После скрытия выполняется `DwmFlush`, а при показе запрашивается свежий кадр
Flutter. При перезапуске композиции DWM её параметры восстанавливаются.
Affinity не сбрасывается в `WDA_NONE` даже на время: такой «ремонт» мог бы
раскрыть содержимое в записи. Если установка исключения возвращает ошибку,
приложение не выполняет новый показ и пишет причину в stderr.

## Проверка на проблемном ПК

1. Полностью завершить прежний Helper и установить/запустить новую сборку.
   Hot reload для этого исправления недостаточно.
2. Проверить локально прозрачность краёв окна и самой панели.
3. Включить запись используемой программой с тем же источником и методом захвата,
   при котором был дефект. Подложить за Helper контрастное статичное окно.
4. Выполнить 20–30 циклов показа/скрытия хоткеем, повторить крестиком и через
   запуск/отмену отсчёта автоввода. Проверить именно сохранённую запись, включая
   первые кадры появления/исчезновения, а не только локальный экран.
5. Повторить после перемещения, изменения размера, смены монитора и масштабирования.
   Отдельно проверить фоновой старт: окно само не открывается.

Есть дополнительный интерактивный сценарий для **реального GDI-захвата экрана**:

```powershell
powershell -ExecutionPolicy Bypass -File tool/test_windows_capture.ps1 -Executable build/windows/x64/runner/Release/helper.exe -Cycles 20
```

Предварительно завершить Helper и восстановить стандартные хоткеи F12/F4.
Во время теста не трогать клавиатуру и мышь. Сценарий показывает контрастный фон,
сравнивает захваченные пиксели до/после показа, проверяет affinity. При расхождении
сохраняет ожидаемый и фактический PNG во временную папку. Тест не включает
автозапуск и не меняет хоткеи, но запускаемое приложение может обновить прежнюю
Run-запись на текущий путь, если автозапуск уже был включён.

GDI-проверка не заменяет OBS/WGC/Teams и не доказывает поведение на другом GPU.
В текущем окружении macOS Win32-композиция и захват не выполнялись.

## Когда чёрный прямоугольник не означает этот баг

- На Windows до 10 2004 `WDA_EXCLUDEFROMCAPTURE` может работать как `WDA_MONITOR`:
  вместо исключённого окна получается чёрная область. Требуется Windows 10 2004+
  или Windows 11.
- Некоторые методы/программы захвата не поддерживают исключение либо сами
  заменяют защищённое окно чёрным. Успех Win32 API не гарантирует результат
  во всех рекордерах. Сравните поддерживаемые методы захвата той же программы.

Если дефект остался, приложите номер сборки из `winver`, модель GPU и версию
драйвера, название/версию рекордера, источник и метод захвата, масштаб мониторов,
а также короткий фрагмент записи. Не отправляйте подготовленные личные тексты.
