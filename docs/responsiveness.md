# Зависание при первом открытии блока и аварийное скрытие

## Что известно

Сообщён редкий случай на Windows 10: первый просмотр импортированного блока
зависает, повторное открытие работает. Без журнала именно этого сбоя причина
не установлена. Это может быть Dart layout/выделение большого текста, первый
проход шрифтов/рендеринга или нативная часть. Успешное повторное открытие не
доказывает отсутствие проблемы.

Выявлен конкретный неограниченный путь: весь текст файла до 32 МБ раскладывался
одним `Text` в `SingleChildScrollView`. SQLite уже работала в отдельном isolate,
но layout оставался на UI isolate. Теперь просмотр разбит на страницы до 8192
UTF-16 единиц; большие тексты подготавливаются в worker isolate. CRLF и пары
суррогатов не разрезаются, соединение страниц даёт исходную строку без потерь.
Для длинных заголовков/описаний ограничено только отображение.

Кнопки «Копировать» и автоввод используют **весь** текст. Исходники, SQLite,
разделение импортов и позиция автоввода не обрезаются. На экране выделяется
только текущая страница. Чтение/подготовка ограничены тайм-аутом 8 секунд;
при асинхронном сбое управление возвращается и можно повторить операцию.
Тайм-аут Dart сам по себе не работает при блокировке всего isolate — для этого
нужен отдельный нативный watchdog.

## Watchdog

После первого UI heartbeat включается независимый нативный поток. Dart посылает
heartbeat раз в секунду (без накопления запросов); Windows-поток отмечается
таймером раз в 500 мс. Если видимая панель более 6 секунд не получает одну из
этих отметок, worker напрямую вызывает `DwmSetWindowAttribute(DWMWA_CLOAK)`
для окна и его нативных диалогов — **без вызова зависшего Dart/оконного обработчика**.
Это попытка аварийного скрытия, а не программное нажатие хоткея в тот же зависший поток.
Если cloak отклонён, дополнительно ставится в очередь `ShowWindowAsync(SW_HIDE)`.

Когда native UI снова отвечает, ввод ставится на паузу и панель прячется обычным
для данной Windows способом (включая парковку на Windows 10). Самостоятельно
обратно она не открывается. Явный показ разрешается только после свежего heartbeat
Dart и обработки аварийного скрытия нативным потоком. Настройки и тексты не удаляются,
процесс не перезапускается и не завершается принудительно самим watchdog.

Начальная загрузка не принимается за зависание: монитор вооружается первым
heartbeat после первого кадра. Уже скрытая панель не вызывает повторных срабатываний.
В интерактивном системном диалоге импорта проверяется native UI, без требования
обслуживать Dart heartbeat внутри модального COM-цикла. При присоединённом отладчике
аварийное скрытие отключено, чтобы breakpoint не считался зависанием.
После длительного сна/паузы сеанса также возможно защитное скрытие, если worker
увидит старые heartbeat раньше, чем возобновятся UI-потоки.

Гарантировать скрытие при зависании DWM, GPU-драйвера или всей Windows нельзя.
Heartbeat также не доказывает исправность каждого кадра GPU: частичный сбой
рендеринга при продолжающих работать потоках может не вызвать срабатывание.
Это защита от пропажи отзывчивости Dart/оконного потока, не универсальное лечение
любого зависания. Тайм-аут 6 секунд — намеренный компромисс против ложных срабатываний.

## Логи без Flutter на проблемном ПК

Для воспроизведения полностью завершить старую версию и запустить новую:

```powershell
& "$env:LOCALAPPDATA\Programs\Helper\helper.exe" --capture-diagnostics
```

Открыть проблемный блок, затем найти последний `capture-*.log`:

```powershell
explorer.exe "$env:LOCALAPPDATA\Helper\Diagnostics"
```

Журнал v3 содержит `block.stage`: 1 — запрос SQLite, 2 — данные получены,
3 — страницы подготовлены и переданы UI, 4 — завершён Dart layout кадра,
5 — чтение/подготовка завершились ошибкой или тайм-аутом.
Это **не** подтверждение показа кадра GPU. Записываются ID и длины, но не текст.
При срабатывании watchdog журнал создаётся автоматически даже без флага и содержит
`watchdog.trip`, возраст native/Dart heartbeat, последнюю стадию/ID/длину и HRESULT cloak.
Подробности до срабатывания доступны, если включён флаг заранее. Прислать журнал,
размер/число строк проблемного блока и уточнить, зависает ли маленький тестовый блок
после полного перезапуска. Личные импортированные тексты отправлять не нужно.

## Проверки разработчика

`flutter test` проверяет разбиение/копирование и heartbeat, отдельный C++-тест —
условия тайм-аута. Это не доказывает DWM cloak или воспроизведение зависания на Windows.

На интерактивном Windows есть контролируемый тест независимости watchdog:

```powershell
powershell -ExecutionPolicy Bypass -File tool/test_windows_watchdog.ps1 -Executable build/windows/x64/runner/Release/helper.exe
```

Предварительно завершить все Helper. Тест запускает собственный экземпляр,
временно приостанавливает **только его native UI thread**, проверяет DWM cloak
из другого процесса, возобновляет поток в `finally` и проверяет явный показ после
восстановления. Не взаимодействовать с рабочим столом во время теста. Затем
повторить обычный тест захвата/Win+Tab, включая восстановление после watchdog.
В текущем окружении macOS этот Win32-тест не выполнялся.
